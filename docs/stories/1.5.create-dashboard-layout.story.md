# Story 1.5: Create Dashboard Layout & Navigation

## Status
Approved

## Story
**As a** authenticated user,
**I want** to see a professional dashboard layout with sidebar navigation (desktop) and hamburger menu (mobile),
**so that** I can easily navigate between different sections like profile and settings.

## Acceptance Criteria

1. [ ] Dashboard layout with sidebar (left) and main content area (right)
2. [ ] Sidebar visible on desktop (1024px+), hidden on mobile (<768px)
3. [ ] Navigation items in sidebar: Home, Profile, Settings
4. [ ] Active route indicator on current navigation item (bold/colored)
5. [ ] Hamburger menu appears on mobile and tablet (<1024px)
6. [ ] Hamburger menu opens sidebar as overlay on mobile
7. [ ] Click outside sidebar closes it on mobile
8. [ ] User avatar in top navbar (right side) from Clerk
9. [ ] Avatar dropdown menu with: Profile, Settings, Logout options
10. [ ] Logout option uses Clerk's SignOutButton
11. [ ] No navigation visible to unauthenticated users
12. [ ] Responsive design works on mobile (375px), tablet (768px), desktop (1024px+)

## Dev Notes

### Dashboard Layout Architecture

**Layout Structure:**
Dashboard uses a two-pane layout (sidebar + content):
- Sidebar (left): Navigation menu, 256px width
- Main area (right): Navbar on top, content below
- Responsive: Sidebar collapses to hamburger on mobile

This layout is standard for SaaS applications and provides excellent UX.
[Source: architecture/project-structure.md, frontend-architecture.md]

**Protected Route Pattern:**
Dashboard layout component checks authentication via `auth()` from Clerk:
- If unauthenticated: redirect to `/sign-in`
- If authenticated: render dashboard layout with navigation
This ensures no dashboard content is visible to non-authenticated users.
[Source: architecture/frontend-architecture.md#protected-route-pattern]

### Component Organization

**Server Components:**
- `app/(dashboard)/layout.tsx` - Can use `auth()` for protection
- `app/components/sidebar.tsx` - Can be server component initially

**Client Components (must be):**
- `app/components/mobile-nav.tsx` - Uses `useState` for menu toggle
- `app/components/user-dropdown.tsx` - Uses `useUser` hook, dropdown interactions
- `app/components/navbar.tsx` - Uses hooks for responsive behavior

[Source: architecture/frontend-architecture.md]

### Responsive Breakpoints

**Tailwind CSS Breakpoints:**
- `sm:` 640px - Small phones
- `md:` 768px - Tablets (sidebar toggle point)
- `lg:` 1024px - Desktops (sidebar always visible)
- `xl:` 1280px - Large desktops

Key breakpoints for this story:
- `md:` Used for sidebar visibility toggle (hidden on mobile, visible on tablet+)
- `lg:` Used for sidebar always visible (desktop only)

[Source: architecture/tech-stack.md]

### Navigation Pattern

**Active Route Detection:**
Use `usePathname()` hook to get current route:
```typescript
const pathname = usePathname();
const isActive = pathname === item.href;
```

Then apply conditional styling:
```typescript
className={isActive ? "font-bold bg-blue-100" : ""}
```

[Source: architecture/frontend-architecture.md]

### Avatar from Clerk

**User Image:**
- `useUser()` hook returns `user` object
- Access image: `user?.imageUrl`
- Display in `<img>` tag or use Clerk's `<UserButton />` for quick integration
- Fallback: show initials or default icon if no image

[Source: architecture/frontend-architecture.md#frontend-example-profile-edit-form]

### Accessibility Considerations

**Mobile Touch Targets:**
- All buttons must be 48px minimum (height or width)
- Use `h-12` or `w-12` in Tailwind for buttons
- Sufficient padding around clickable areas

**Semantic HTML:**
- Use `<nav>` for navigation sections
- Use `<a>` tags with proper `href` for links
- Use `<button>` for interactive elements

**Keyboard Navigation:**
- All components must be keyboard accessible
- Dropdown menu accessible via Tab and Arrow keys (shadcn/ui handles this)
- Hamburger menu must be triggerable with Enter/Space

[Source: architecture/security-performance.md]
